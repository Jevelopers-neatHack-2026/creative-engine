# Direct OpenAI Images adapter

Checked against the official Images generation and edit references on 2026-10-10:

- [Create image](https://developers.openai.com/api/reference/resources/images/methods/generate)
- [Create image edit](https://developers.openai.com/api/reference/resources/images/methods/edit)

This is documentation evidence only. The `gpt-image-2.5-sunburst-2026-09-08` and `gpt-image-2.5-flare-2026-09-08` profiles are candidate pins, marked `candidate_unselected`. No account, organization, project, model entitlement, quota, price, image quality, or pixel-level behavior is inferred from documentation. Both candidates still need owner selection, live access evidence, and evaluation before promotion.

The adapter uses native `fetch`, reports its exact Node version in the route, and calls only the direct generation endpoint (`POST /v1/images/generations`) or edit endpoint (`POST /v1/images/edits`). It fixes `n=1`, does not stream, and expects one base64 image in the response. Generation sends JSON and does not send reference images. Edit sends multipart form data with the immutable selected parent image as the first `image[]`, then up to 15 additional references from the versioned `CreativeImageReferenceManifest`; the documented Images edit endpoint accepts up to 16 images. A scoped PNG mask may also be sent. The manifest binds the tenant, project, brief/hash, current research package/hash, parent design version/hash, and each reference source, asset ID, content hash, MIME type, and dimensions. The API independently checks those bindings, current package permission, a trusted short-lived permission proof, and the durable asset fence around asynchronous work. The adapter resolves bytes through a scoped asset port and checks their hash, format, and dimensions before multipart serialization. Arbitrary URLs and caller-supplied bytes are not accepted. Each input is limited to 50 MiB and combined parent/reference/mask bytes to 100 MiB. The local multi-reference extension remains subject to consumer and owner review; CE-04's two-reference concept scenarios and CE-07 geometry/drift requirements remain separate acceptance work.

Every call requires an already validated C03 `reservation_ref`, distinct operation, billable, transport, reservation, and dispatch identities, an active abort signal, and a deadline. Provider-input JSON is snapshotted before its first asynchronous port call. The authorization binding includes the exact model, endpoint, operation, configuration hash, attempt, reservation, deadline, stop policy, plan hash, rendered-prompt hash, input hash, and immutable parent/mask byte hashes when editing. Before any provider request, the local adapter contract requires trusted per-operation account/project capability and quota evidence, an exact access grant, a held Finance reservation, a matching currency and authorized spend cap, scoped credential resolution, and matching provider organization/project routing. These port shapes are implementation proposals for offline fixtures, not accepted external Finance, access, credential, or capability protocols.

After C03 confirms the transport identity, the adapter revalidates grant, Finance lease, and model capability, then performs a final synchronous cancellation, deadline, expiry, revocation, and identity check immediately before `fetch`. The independent authorities do not provide one atomic cross-authority revocation read; the implementation makes sequential checks and does not claim atomicity. If a check fails after C03 records transport, the outcome is unknown and the reservation remains held for reconciliation. No output is published after cancellation, timeout, malformed response, or an unknown provider outcome.

The accepted option subset is explicit: `quality` is `low`, `medium`, `high`, `xhigh`, or `max`; `size` is `auto` or a dimension string whose sides are multiples of 16, aspect ratio is between 1:3 and 3:1, and edges are at most 3840×2160; `output_format` is PNG, JPEG, or WebP; `background` is opaque or transparent, with transparent output limited to PNG/WebP; `moderation` is `auto` or `low`. Resolutions above 2560×1440 are experimental in the official reference and still require exact account/model capability proof. `input_fidelity`, `response_format`, streaming, URL output, multiple generated images, animated output, and alias upgrades are not sent. Unsupported configuration is rejected before transport.

Image bytes are bounded, decoded from canonical base64, and checked against the requested format and dimensions. PNG validation checks chunk CRCs, bounded decompression, scanline filters, dimensions, and alpha; indexed and interlaced PNGs are rejected. JPEG validation accepts bounded baseline sequential images and validates quantization/Huffman tables and the complete coded scan; progressive JPEG is rejected. Still WebP images pass RIFF/frame checks; animation and separate-alpha chunks are rejected. All three formats are then fully decoded into RGBA pixels by pinned `sharp` 0.35.5 (libvips 8.18.7, libwebp 1.6.0), so header-only and corrupt compressed payloads are rejected. The decoder enforces at most 16,777,216 pixels, a 64 MiB decoded RGBA buffer, and a 30-second processing timeout, then clears the temporary pixel buffer. For 16-bit sources it preserves `ushort` alpha values through decoding, and counts the 8-byte-per-pixel RGBA buffer against the same 64 MiB cap; that byte cap can lower the accepted pixel count below the separate pixel limit. Edit masks must be PNGs with actual transparent alpha pixels and dimensions matching the immutable parent artwork. Maximum input and output bytes are 50 MiB. The runtime is declared in the isolated `src/models/codec-runtime` package and lockfile; sharp is Apache-2.0, the bundled libvips package is LGPL-3.0-or-later, and libwebp is New BSD. The lockfile records platform package integrity hashes. Reproduce installation with `npm ci --prefix src/models/codec-runtime`; this package uses sharp's official prebuilt binaries where available and fails closed with `image_decoder_unavailable` if loading the pinned decoder fails. The cited sharp install documentation lists Linux x64 prebuilt requirements including glibc 2.28+ and SSE4.2. Tests here ran on macOS arm64 with Node 22.23.3 and 24.15.0; the deployment libc, native installer, and any CloudLinux cage restrictions have not been verified, so no target-host compatibility is claimed. See [sharp installation](https://sharp.pixelplumbing.com/install/), [constructor limits and timeout](https://sharp.pixelplumbing.com/api-constructor/), and [raw pixel output](https://sharp.pixelplumbing.com/api-output/).

Provider `usage` is returned as allowlisted raw counters, preserving `input_tokens`, `output_tokens`, `total_tokens`, and nested text/image details when present. The public provider-request reference is a stable SHA-256 alias; transport identity remains the exact validated C03 transport ID. The raw provider request ID is recorded through the restricted CE08 attribution port and is never copied into public JSON, error messages, C03 observations, or public references. Bounded normalized counters and their hash are recorded in an append-only private attribution table on the same SQLite connection; the stored usage record contains only the safe provider-request alias. If usage was actually parsed before cancellation, refusal, malformed output, or another failed result, `OpenAIImagesProviderError.usage` carries the same sanitized counters and identities as an observation only. It does not publish artwork or imply settlement; absent or unreadable usage is left absent rather than filled with zeroes.

The current GPT Image 2.5 candidate has no accepted usage-to-rate mapping in the contract profile, so the default runtime reports unknown completeness and a mapping-pending field. A host may inject `telemetry.usage_profile_authority.mapProviderUsage`; the runtime binds that result to the exact attempt, reservation, dispatch intent, transport, target hash, provider identity, outcome, and raw usage hash, validates the C03 observation, then rechecks current brief/asset rights, job authorization, and deadline before C03 can settle. Without a matching trusted map, the hold remains. The integrated intercepted fixture contains a clearly labeled MOCK owner profile solely to exercise the positive native bytes → API → C03 → CE08 path. It is not a selected GPT Image 2.5 profile, Finance acceptance, or live evidence. No local price arithmetic or assumed complete usage is allowed.

There is no automatic retry. `Retry-After` seconds or HTTP dates are parsed into an advisory decision bounded by attempt count, elapsed time, delay, and deadline. An eligible next attempt still requires separate fresh grant/capability/Finance authorization, a new billable attempt, a new reservation, and a new transport identity. Authentication, permission, quota exhaustion, moderation, and malformed requests are hard stops. A timeout after transport has unknown completion; the adapter does not invent idempotency keys, assume output retrieval, or retry image generation. Retrying byte validation, storage, or observation must never repeat the paid request.

Live operation remains blocked until the real owners provide accepted account/project capability and quota evidence, grant and credential bindings, Finance reservation/lease/cap semantics, and usage mapping. This branch now includes the local API/C03/CE08/CE11 integration, durable byte publication, and private usage attribution exercised with intercepted fixtures. Those fixtures contain synthetic responses and do not establish live access, model selection, or canonical Finance agreement. The live gate reads no credentials and makes zero provider requests. Relevant acceptance remains open: ART-01, FIN-01, FIN-03, FIN-04, and AGT-03.
